# Архитектурные решения (ADR)

Формат: MADR-lite. Статус: Accepted (черновик, может уточняться по ходу хакатона).

## ADR-0001: Визуальный редактор на React Flow

- **Статус:** Accepted
- **Контекст:** Нужен drag-and-drop конструктор графа нод с соединениями, зумом, панорамированием, кастомными нодами. ТЗ разрешает библиотеки визуализации графов (React Flow, Rete.js и аналоги), но запрещает готовые workflow-платформы (n8n, Node-RED).
- **Решение:** Использовать `react-flow` (React Flow) для холста, палитры и соединений. Прикладная логика нод и движок выполнения — собственные.
- **Последствия:** Быстрая реализация UI; кастомные ноды через React-компоненты; зависимость от библиотеки, но она зрелая и поддерживает TS. Логика выполнения не привязана к React Flow (только представление).

## ADR-0002: Бэкенд на Express (Node.js)

- **Статус:** Accepted
- **Контекст:** Нужен HTTP API для запуска workflow и получения статуса, CORS для Pages, простота и скорость разработки в 48-часовом хакатоне. Альтернативы: Fastify, NestJS.
- **Решение:** Express 4 + `cors` + `express.json()`. Валидация входных данных — Zod.
- **Последствия:** Минимальный boilerplate, широкая экосистема middleware (helmet, rate-limit — планируются). Меньшая производительность vs Fastify, но для прототипа достаточно. NestJS избыточен для MVP.

## ADR-0003: In-memory store для результатов запусков

- **Статус:** Accepted (MVP)
- **Контекст:** История запусков и логи выполнения нужны для визуализации и демо. Времени на БД в Фазе 1–2 нет; персистентность не критична для прототипа.
- **Решение:** Хранить запуски, статусы нод, находки и логи в in-memory Map на бэкенде.
- **Последствия:** Простота и скорость. Данные теряются при рестарте сервера. Миграция на SQLite/Postgres — задача со звёздочкой / Фаза 4+ (если останется время). На GitHub Pages бэкенд вообще не деплоится, поэтому in-memory достаточен для локального демо.

## ADR-0004: LLM-интеграция как адаптер (не замена сканерам)

- **Статус:** Accepted
- **Контекст:** ТЗ требует LLM для агрегации, объяснения и рекомендаций поверх результатов собственных анализаторов. Запрещено использовать LLM вместо SAST/SCA/поиска секретов. Дополнительно: поддержка закрытого контура (локальные модели).
- **Решение:** Выделить AI-модуль с интерфейсом `LLMAdapter { complete(prompt): Promise<string> }`. Конкретная реализация (OpenAI/Claude/локальная через Ollama/vLLM) выбирается настройкой (env/config). Промпт содержит только агрегированные находки и требует структурированный JSON-ответ (объяснение, рекомендации, ссылки на файлы/строки). Ответ валидируется по схеме; выдуманные CVE отбрасываются.
- **Последствия:** Легко переключать провайдера; тестируемость через mock-адаптер. Добавляется слой валидации ответа LLM. Сканеры остаются единственным источником находок.

## ADR-0005: Модульная регистрация типов нод

- **Статус:** Accepted
- **Контекст:** Требование расширяемости: добавление нового типа ноды с минимальными изменениями основного кода.
- **Решение:** Реестр нод: тип → { schema (Zod), defaultParams, executor, uiComponent }. Движок ищет executor по типу; React Flow рендерит uiComponent по типу. Новые типы регистрируются в одном месте (манифест).
- **Последствия:** Добавление ноды = новый модуль + регистрация, без правки движка/редактора. Требует дисциплины при регистрации.

## ADR-0006: Shared-типы в `src/shared`

- **Статус:** Accepted
- **Контекст:** FE и BE должны использовать одинаковые контракты (Node, Edge, Workflow, Finding и т.д.).
- **Решение:** Общие TS-типы и Zod-схемы живут в `src/shared/types`; алиасы `@shared/*` настраиваются в tsconfig и Vite.
- **Последствия:** Единый источник истины. Изменения координируются через DATA-трек (см. AGENTS.md).

# План на 30 часов — OGMOP Hackathon

> Непрерывная параллельная работа сотен агентов под управлением ДИРЕКТОРА.
> ТЗ находится в `D:\OGMOP\ТЗ\`. При изменении ТЗ — директор перестраивает план.

## Принципы распределения

1. **3 уровня**: Директор → Командиры (7) → Рабочие (сотни).
2. **Параллелизм**: все независимые задачи запускаются одновременно (Promise.all).
3. **Изоляция**: один файл — один агент. Конфликты разрешает командир.
4. **Частые коммиты**: каждые 5–15 мин или после задачи → push → автодеплой.
5. **Откат**: каждая фаза = тег `v0.x.0`. При проблеме — откат к тегу.
6. **Метрики прогресса**: % задач Done, успешность сборки, покрытие тестами.

## Треки (параллельные потоки)

| Трек | Командир | Зона | Рабочие |
|------|----------|------|---------|
| FE | commander-frontend | src/frontend, public | coder, tester, reviewer, docs |
| BE | commander-backend | src/backend | coder, tester, reviewer |
| DATA | commander-data | src/backend/models, migrations, shared/types | coder, tester |
| DEVOPS | commander-devops | .github, scripts, Docker | devops, coder |
| QA | commander-qa | tests | tester, reviewer |
| DOCS | commander-docs | docs, README | docs |
| SEC | commander-security | middleware, auth | coder, reviewer |

## Фаза 0 — Анализ и декомпозиция (0–2 ч)

**Цель**: понять ТЗ, создать детальный план задач, настроить инфраструктуру.

- [0:00–0:30] Директор читает ТЗ из `D:\OGMOP\ТЗ\`, уточняет требования у заказчика.
- [0:30–1:00] Директор декомпозирует на эпики → фичи → атомарные задачи.
- [1:00–1:30] Командиры получают эпики, создают очередь задач для своих треков (параллельно).
- [1:30–2:00] DEVOPS: проверяет CI/CD, Pages, скрипты. DOCS: создаёт структуру docs. QA: настраивает тест-фреймворк.
- **Выход**: `docs/backlog.md` с полным списком задач по трекам; тег `v0.0.0`.

## Фаза 1 — Каркас MVP (2–8 ч)

**Цель**: рабочий скелет приложения на GitHub Pages.

Параллельные потоки:

### DEVOPS (2–4 ч)
- Настроить Vite/React скелет (уже есть базовый).
- GitHub Actions: lint, test, build, deploy.
- Скрипты: dev, build, preview, test, lint.
- **Критерий**: `npm run build` зелёный, Pages доступен.

### FE (2–6 ч)
- Layout: Header, Footer, Navigation.
- Routing (react-router).
- Дизайн-система: цвета, типографика, компоненты (Button, Card, Input).
- Главная страница-заглушка.
- **Критерий**: страницы рендерятся, навигация работает.

### BE (2–6 ч)
- Express сервер: health, CORS, helmet, rate-limit.
- Структура routes/services/models.
- Мок-данные (in-memory) для фронта.
- **Критерий**: `/api/health` отвечает, контракты описаны.

### DATA (2–6 ч)
- Shared types (TS) для FE и BE.
- Схемы сущностей из ТЗ.
- Seed-данные.
- **Критерий**: типы компилируются, seed загружается.

### DOCS (2–4 ч)
- README с инструкциями запуска.
- Архитектурный обзор.
- API-контракты (черновик).

### QA (4–6 ч)
- Настроить Vitest + React Testing Library.
- Smoke-тесты для сборки.
- **Критерий**: `npm test` зелёный.

**Выход**: тег `v0.1.0` (MVP-каркас на Pages).

## Фаза 2 — Основной функционал (8–16 ч)

**Цель**: реализовать все user stories из ТЗ.

Директор распределяет фичи между треками. Каждая фича = набор задач для FE+BE+DATA+QA.

Типичный цикл фичи (2–4 ч):
1. DATA: типы и модели.
2. BE: эндпоинты.
3. FE: UI-компоненты и страницы.
4. QA: тесты.
5. DOCS: обновление.
6. SEC: аудит.

**Параллелизм внутри фичи**: DATA и BE могут идти параллельно после согласования контракта; FE — после готовности контракта; QA — после FE/BE; SEC — параллельно с QA.

**Критерий фазы**: все P0-фичи из ТЗ реализованы, сборка зелёная, базовые тесты проходят. Тег `v0.2.0`.

## Фаза 3 — Интеграция и полировка (16–22 ч)

**Цель**: связать фичи, улучшить UX, исправить баги.

- FE: адаптивность, анимации, состояния загрузки/ошибок, доступность.
- BE: обработка ошибок, валидация, логирование.
- QA: интеграционные и e2e тесты (Playwright/Cypress).
- SEC: полный аудит, исправление уязвимостей.
- DOCS: полная документация, CHANGELOG.
- **Критерий**: все P1-фичи, e2e проходят, Lighthouse ≥ 80. Тег `v0.3.0`.

## Фаза 4 — Оптимизация и надёжность (22–26 ч)

**Цель**: производительность, стабильность, готовность к демо.

- FE: code-splitting, lazy loading, оптимизация бандла.
- BE: кэширование, rate-limit, graceful shutdown.
- QA: нагрузочное тестирование, регрессия.
- DEVOPS: мониторинг, алерты (опционально).
- DOCS: финальная документация, инструкции деплоя.
- **Критерий**: бандл ≤ 200kb gzip, время ответа ≤ 300ms. Тег `v0.4.0`.

## Фаза 5 — Финал и демо (26–30 ч)

**Цель**: финальный релиз и подготовка к презентации.

- [26–27] Финальная сборка, проверка Pages.
- [27–28] Подготовка демо-сценария (DOCS).
- [28–29] Буфер: исправление критических багов (все треки).
- [29–30] Финальный деплой, тег `v1.0.0`, отчёт заказчику.

## Управление параллелизмом

### Распределение задач
- Директор держит `docs/backlog.md` с задачами по статусам: Todo / In Progress / Done / Blocked.
- Каждые 30 мин — синхронизация: командиры отчитываются, директор перераспределяет.
- Блокеры эскалируются немедленно.

### Избежание конфликтов
- Один файл — один агент. Командир следит за `git status`.
- Shared-типы: изменения только через DATA-командира, с уведомлением FE и BE.
- Конфликты merge: командир трека разрешает, при сложности — директор.

### Частота обновлений
- Автокоммит каждые 5 мин (Scheduled Task).
- Push после каждой завершённой задачи.
- Деплой Pages автоматически.
- Заказчик видит прогресс на сайте в реальном времени.

### Откат
- Каждая фаза = git-тег.
- При критическом баге: `git revert` конкретного коммита.
- При провале фазы: откат к тегу предыдущей фазы.

## Адаптация под ТЗ

1. Заказчик кладёт ТЗ в `D:\OGMOP\ТЗ\`.
2. Директор читает все файлы (md, txt, pdf, docx, изображения).
3. Директор строит `docs/backlog.md` с конкретными задачами.
4. Командиры распределяют между рабочими.
5. План выше — каркас; конкретные фичи подставляются из ТЗ.

> Если ТЗ меняется в процессе — директор перестраивает backlog, команда продолжает с новым планом.

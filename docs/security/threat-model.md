# Threat Model — OGMOP (Cyber Garden 2026)

Дата: 2026-11-20. Автор: commander-security.

## 1. Контекст и границы

OGMOP — визуальная платформа автоматизации проверок безопасности кода.
Состоит из:
- Frontend (React + Vite) — работает в браузере пользователя.
- Backend (Node.js/Express) — API, оркестрация workflow, запуск сканеров.
- Shared types (Zod) — валидация контрактов.
- Внешние интеграции: LLM API (OpenAI/Claude), Telegram/SMTP/webhook, Git-репозитории (только тестовые/учебные).

Доверенные границы:
- Пользователь ↔ Frontend (браузер).
- Frontend ↔ Backend API (HTTPS в проде, HTTP локально).
- Backend ↔ LLM/уведомления/репозитории (исходящие запросы).

Недоверенные входы: JSON-тела запросов, query/params, загруженные файлы/репозитории, ответы LLM, входящие webhook.

## 2. Активы (Assets)

| ID | Актив | Критичность |
|----|-------|-------------|
| A1 | Исходный код сканируемых репозиториев | High |
| A2 | Секреты пользователей (токены Telegram, SMTP, Git, LLM API keys) | Critical |
| A3 | Результаты сканирования и отчёты LLM | Medium |
| A4 | Учётные данные пользователей (если auth) | Critical |
| A5 | Доступность сервиса (API) | High |
| A6 | Целостность workflow-конфигураций | Medium |
| A7 | Логи выполнения | Low/Medium |

## 3. Акторы

- Пользователь (разработчик/безопасник) — доверенный, но может ошибаться.
- Анонимный клиент / бот — недоверенный.
- Внешний LLM-провайдер — частично доверенный (данные уходят наружу).
- Владелец тестового репозитория — доверенный источник данных.
- Атакующий в сети (MITM) — недоверенный.

## 4. STRIDE-анализ

### S — Spoofing (подмена личности)
- S1. Подделка JWT/токена → доступ к чужим workflow/результатам.
  Меры: подпись JWT секретом из env, проверка issuer/audience, httpOnly+Secure+SameSite cookies (если cookies), короткий TTL + refresh.
- S2. Подмена webhook-источника → запуск workflow от имени системы.
  Меры: верификация подписи webhook (HMAC), allowlist IP/секрет в query.

### T — Tampering (искажение данных)
- T1. Изменение тела запроса (workflow JSON) → инъекция произвольных нод/команд.
  Меры: Zod-валидация схем, whitelist типов нод, лимиты размера тела.
- T2. Path traversal при чтении файлов репозитория → чтение произвольных файлов хоста.
  Меры: нормализация пути, проверка что путь внутри разрешённого корня, запрет `..`.
- T3. Подделка ответа LLM (prompt injection) → выполнение нежелательных действий.
  Меры: LLM используется только для объяснения/рекомендаций, не для принятия решений; строгий парсинг JSON-схемы; игнорирование инструкций в данных.

### R — Repudiation (отрицание)
- R1. Отсутствие аудита действий → невозможно расследовать инцидент.
  Меры: структурированные логи (без секретов), correlation-id, запись запусков workflow.

### I — Information Disclosure (раскрытие информации)
- I1. Утечка секретов в логах/ответах API.
  Меры: маскирование секретов (utils/secrets.js), не логировать токены, не возвращать их в API.
- I2. Раскрытие стек-трейсов/внутренних ошибок.
  Меры: централизованный error handler, generic-сообщения в проде, логирование деталей только сервер-side.
- I3. CORS misconfiguration → доступ из любого origin.
  Меры: явный allowlist origin из env.
- I4. Отправка секретов пользователя в LLM.
  Меры: не передавать токены/ключи в промпт; маскировать найденные секреты в отчёте.

### D — Denial of Service (отказ в обслуживании)
- D1. Флуд запросами → перегрузка API.
  Меры: rate-limit (express-rate-limit) per IP, лимиты размера тела.
- D2. Загрузка огромного репозитория/файла → OOM.
  Меры: лимиты размера, таймауты, лимит числа файлов, streaming.
- D3. ReDoS в regex-сканерах.
  Меры: таймауты regex, ограничение длины входа, тесты на catastropic backtracking.

### E — Elevation of Privilege (повышение привилегий)
- E1. Инъекция команд (command injection) при запуске git/сканеров.
  Меры: не использовать shell с пользовательским вводом; execFile с массивом аргументов; валидация URL репозитория.
- E2. SSRF через URL репозитория/webhook → доступ к внутренним сервисам.
  Меры: валидация URL, блокировка приватных IP/localhost/metadata, allowlist схем.
- E3. NoSQL/SQL injection — не применимо (in-memory), но валидация всё равно.
- E4. XSS в отображении результатов (имена файлов, фрагменты кода).
  Меры: экранирование на фронте (React по умолчанию), CSP, санитизация.

## 5. Требования безопасности (Security Requirements)

1. Секреты только через env/GitHub Secrets; в коде — none.
2. Все входы валидируются Zod-схемами.
3. CORS: явный allowlist origin.
4. Helmet + CSP headers.
5. Rate-limit на всех публичных эндпоинтах.
6. Лимит размера тела (≤ 1MB по умолчанию).
7. Централизованный error handler без утечки стеков.
8. Маскирование секретов в логах.
9. Path traversal защита.
10. SSRF защита для URL репозиториев/webhook.
11. Не выполнять shell с пользовательским вводом.
12. Аудит зависимостей (npm audit) — нет critical/high.

## 6. Вне скоупа (Out of scope)

- Полноценная multi-tenant изоляция (MVP — single user / demo).
- WAF/CDN защита.
- Полный Vault (MVP — env + простое шифрование настроек).

## 7. Меры, реализованные в коде

- `src/backend/middleware/security.js` — applySecurity(app): helmet, CORS, rate-limit, body limit, CSP, error handler.
- `src/backend/middleware/validate.js` — Zod middleware factory.
- `src/backend/auth/` — optional authenticate middleware (JWT-ready).
- `src/backend/utils/secrets.js` — mask/encrypt helpers.
- `docs/security/audit.md` — отчёт аудита секретов и зависимостей.

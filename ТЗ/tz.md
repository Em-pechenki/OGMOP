О чем этот кейс?
Небольшие команды и стартапы часто выпускают продукт в сжатые сроки, и безопасность кода у них держится на внимательности самих
разработчиков. В отрасли хорошо известны типовые ошибки: случайно оставленные в коде тестовые ключи, устаревшие библиотеки с
опубликованными уязвимостями, неточности в проверке прав доступа. Обнаруженные после релиза, они обходятся дороже всего.

В крупных организациях, включая банки, для этого выстроены процессы безопасной разработки и используются профессиональные
инструменты. Небольшим командам такие решения часто недоступны или сложны в настройке. Этот кейс предлагает сделать подобную
проверку доступной: визуальный конструктор, где сценарий собирается из блоков, а AI объясняет найденные проблемы простым языком.
Цель
Основной целью кейса является создание платформы визуальной автоматизации проверок безопасности, позволяющей без написания кода
собирать и запускать сценарии (workflow) из взаимосвязанных блоков (нод). В качестве примера визуального подхода к построению
сценариев можно ориентироваться на n8n: пользователь добавляет ноды, настраивает их параметры и соединяет между собой в логические
цепочки. Платформа должна автоматически выявлять потенциальные уязвимости и предупреждать команду о рисках безопасности.

Сервис должен помогать принимать решения: объяснять простым языком, где именно в коде возникла угроза, насколько она критична и
какие конкретные шаги нужно предпринять для ее устранения.

Благодаря этому сервису у разработчиков должна быть возможность заранее выявлять и исправлять ошибки безопасности до выхода
продукта, не разбираясь самостоятельно в сложных корпоративных сканерах и громоздких технических отчетах.
Основные задачи
1. Создание визуального drag-and-drop конструктора сценариев
Сервис должен предоставлять удобный редактор, в котором пользователь может добавлять готовые блоки (ноды), настраивать их параметры и
соединять между собой в логические цепочки. Это позволит настраивать сложные процессы проверки безопасности без написания кода.
2. Реализация базовых нод запуска, логики и оповещений
Сервис должен включать триггеры для старта проверки (по кнопке, расписанию), логические условия ветвления (if/else, сравнение, регулярные
выражения) и ноду уведомлений с одним каналом на выбор (Telegram, SMTP или HTTP webhook). Это позволит управлять сценарием и
доставлять результаты проверки.
3. Разработка собственных нод проверки безопасности и классификации угроз
Сервис должен содержать собственные базовые анализаторы для поиска секретов, проверки уязвимых зависимостей (SCA) и базового
статического анализа (SAST) Kotlin-приложений на Spring Boot с Gradle (Kotlin DSL), а также определять уровень критичности каждой находки.
Это позволит выявлять и ранжировать потенциальные риски без готовых сканирующих движков.
Основные задачи
4. Внедрение AI-анализа и генерации рекомендаций
Сервис должен передавать результаты проверок в языковую модель (LLM), которая агрегирует найденные ошибки, объясняет риски простым
языком и предлагает способы исправления. Это позволит разработчикам быстро понимать суть проблемы и устранять уязвимости без глубоких
знаний в области информационной безопасности.

5. Визуализация процесса выполнения сценария
Сервис должен наглядно отображать ход работы запущенного workflow в реальном времени: показывать статус каждого блока и передаваемые
между ними данные. Это позволит пользователю легко отслеживать работу системы и находить ошибки в настройке самого сценария.
Задачи со звёздочкой
1. Публикация и библиотека готовых шаблонов сценариев
Создавать сложные цепочки проверок с нуля каждый раз неудобно. Чтобы ускорить запуск проверок для новых проектов, система дол жна
позволять делиться удачными настройками и переиспользовать их:
- публикация созданного workflow в общую библиотеку шаблонов с описанием задач, которые он решает;
- просмотр и копирование понравившегося сценария к себе в рабочее пространство;
- гибкое редактирование скопированного шаблона под параметры своего репозитория и каналов оповещения.

Каждый опубликованный шаблон становится готовым инструментом, который другие пользователи могут запустить в пару кликов.

2. Интеграция workflow как шага (job) в CI/CD пайплайн
Ручной запуск проверок зависит от человеческого фактора. Чтобы контроль безопасности стал неотъемлемой частью разработки, система
должна встраиваться в автоматический процесс сборки кода:
- генерация готовой конфигурации для CI/CD или реализация механизма запуска workflow из пайплайна через HTTP API, webhook либо
    другой подходящий способ (GitHub Actions, GitLab CI или аналоги);
- автоматический старт проверки при каждом новом коммите или создании запроса на слияние (Pull/Merge Request);
- возврат статуса выполнения обратно в пайплайн, чтобы команда сразу видела результат проверки безопасности.

При обнаружении критических уязвимостей система должна сигнализировать об ошибке на этапе сборки и предупреждать команду до
попадания проблемного кода в основной продукт.
Задачи со звёздочкой
3. Генерация сценария по текстовому описанию с помощью AI
Настройка нод и логических условий требует времени даже в визуальном редакторе. Чтобы разработчики могли быстрее создавать повторяемые
проверки безопасности, система может собирать цепочки по обычному запросу на естественном языке:
- ввод текстовой задачи в свободной форме (например: «Каждый день в 14:00 проверяй код из репозитория на наличие секретов и отправляй
    отчет на почту»);
- автоматическое распознавание нужных триггеров, сканеров и каналов связи с помощью языковой модели;
- мгновенная отрисовка готового и преднастроенного workflow на рабочем экране.

После генерации пользователь может сразу запустить созданный сценарий или вручную подправить параметры отдельных блоков.
Технические требования
Минимальные
1. Работающий прототип
Прототип должен принимать файлы или ссылку на учебный репозиторий Kotlin-приложения на Spring Boot с Gradle, выполнять собранный
пользователем workflow и отправлять итоговое уведомление с отчетом о потенциальных уязвимостях. Сами анализаторы и платформу
разрешается разрабатывать с использованием любого стека.

2. Собственные модули проверки безопасности (без готовых сканеров)
Реализовать собственные базовые анализаторы для поиска секретов, проверки зависимостей (SCA) и статического анализа (SAST) Kotlin-
проектов на Spring Boot с Gradle и оценкой критичности. Запрещено использование LLM вместо собственных анализаторов для обнаружения
уязвимостей, готовых сканеров и их движков (Semgrep, Gitleaks, Trivy, detekt с готовыми security-правилами), а также прямое использование
чужих наборов правил. Разрешены regex, парсеры, Kotlin PSI/tree-sitter, библиотеки сравнения версий и справочники уязвимостей. Допускаются
собственные эвристические правила.

3. Интеграция LLM
Реализовать интеграцию с доступной LLM для объяснения и обобщения результатов собственных анализаторов (не для замены
SAST/SCA/поиска секретов). Допустимы бесплатные API и локальные модели; платная подписка не требуется. Проверять структуру ответа,
соответствие найденным файлам/строкам и отсутствие выдуманных CVE. Мощность и размер модели не оцениваются.
Технические требования
Минимальные
4. Интерфейс: визуальный редактор и отображение выполнения
Интерфейс должен предоставлять drag-and-drop конструктор нод и показывать статусы и результаты выполнения. Разрешено использование
библиотек визуализации графов (React Flow, Rete.js и аналоги) и готовых workflow-движков для исполнения сценариев (Flowable, Temporal,
Conductor и аналоги). При этом использование готовых workflow-платформ (n8n, Node-RED и аналоги) в качестве основы решения не
допускается. Визуальный конструктор и прикладная логика нод должны быть реализованы участниками самостоятельно.

5. Соблюдение ограничений по безопасности
Сканирование допускается только на предоставленных организаторами репозиториях и собственных безопасных учебных проектах.
Проверка любых систем, кроме предоставленного тестового репозитория, запрещена.
Технические требования
Дополнительные. Будет плюсом при оценке архитектуры.
1. Модульная и расширяемая архитектура
Система должна быть спроектирована так, чтобы добавление нового типа ноды (например, еще одного сканера или нового
мессенджера) требовало минимальных изменений в основном коде.

2. Поддержка работы в закрытом контуре (локальные LLM)
Архитектура модуля ИИ должна позволять переключаться между внешними API и локально развернутыми моделями (например, через
Ollama или vLLM) простой сменой настроек без переписывания логики. Это критически важно для корпоративной безопасности.

3. Безопасное хранение настроек и секретов (шифрование / Vault)
Поскольку пользователь вводит в настройках нод токены от Telegram, пароли от почты или ключи от репозиториев, система должна
хранить их в зашифрованном виде и маскировать в интерфейсе, а не передавать открытым текстом в логах.

4. История запусков и логирование выполнения
Помимо живого отображения процесса, полезно сохранять историю всех прошедших проверок: когда запускался сценарий, какие
уязвимости были найдены в прошлый раз и какой отчет сгенерировала нейросеть.
Входные данные для разработки
Для разработки выдается открытый учебный Kotlin/Spring Boot-проект на Gradle. Финальная проверка проводится на отдельной скрытой
вариации с теми же классами проблем. Оба проекта содержат только синтетические данные.

Обязательные элементы тестового набора:
-          файлы исходного кода с намеренно оставленными секретами (пароли, API-ключи, токены);
-          файлы Gradle Kotlin DSL (build.gradle.kts) и конфигурации Spring Boot с уязвимыми зависимостями;
-          фрагменты кода с простыми логическими ошибками безопасности (для проверки SAST);
-          справочник уязвимостей для SCA в JSON с нормализованными диапазонами версий;
-          эталонные находки для открытого проекта.

Вычислительные мощности и ключи к языковым моделям организаторами не предоставляются, команды используют любые бесплатные
облачные API или локальные модели на своих ресурсах.
